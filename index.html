How Ansible Works

This page was installed on this server automatically by an Ansible playbook. Here is how.

What is Ansible?

Ansible is an open-source automation tool from Red Hat. You describe how your servers should look in simple YAML files, and Ansible makes them that way: installing packages, copying files, configuring and starting services.

Instead of logging in to every server and typing commands by hand, you write the steps once, keep them in Git, and run them on one server or hundreds. Every server ends up configured the same way, every time.

How it connects

Ansible runs on a control node and pushes changes over SSH to the managed nodes it configures. Nothing needs to be installed on the managed nodes apart from SSH and Python: Ansible is agentless.

The key building blocks

Inventory

A list of the servers Ansible manages, organised into groups such as web or db.

Module

A small unit of work, such as apt to install a package or copy to send a file.

Task

One step that calls a module with settings, for example "install nginx".

Playbook

A YAML file listing tasks to run against a group of hosts, in order.

Role

A reusable bundle of tasks, templates and variables that teams can share.

Idempotency

Running the same playbook again changes nothing if the server is already correct.

How this page got here

This server started as a bare Ubuntu container. A playbook with three tasks did the rest:

# site.yml
- name: Configure web server
  hosts: web
  become: true

  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present

    - name: Copy custom homepage
      ansible.builtin.copy:
        src: files/index.html
        dest: /var/www/html/index.html

    - name: Start nginx
      ansible.builtin.service:
        name: nginx
        state: started

What happens when you run a playbook

  1. Read the inventory to find which servers are in the target group.
  2. Connect over SSH to each server with the configured user and key.
  3. Gather facts about each server: operating system, IP addresses, memory.
  4. Run each task in order: copy the module over, run it with Python, get the result back, clean up.
  5. Print the PLAY RECAP summarising what happened on every server.

Reading the results

StatusMeaning
okAlready correct. Nothing needed changing.
changedAnsible made a change to reach the desired state.
failedThe task hit an error, so Ansible stops on that server.
Idempotency in action: the first run of this playbook reports changed for each task. Run it again and it reports changed=0, because nginx is already installed, this page is already in place and the service is already running.
